# API stability and hierarchy

## Post-0.12 stability posture

`0.12.0` is a closed scientific release. The active source line is
`1.0.0rc1`, but the project is **not** treating the next version number as a
reason to add another estimator tranche.

The completed post-0.12 observation programme now supports an explicit 1.0
stabilization boundary. `ONE_DOT_ZERO_API_STABILITY.json` is the frozen
machine-readable contract generated from exact protected-main baseline
`382c5940e090faf0f74f9bce4e9180a9e14f1eca`.

The boundary contains **458 public exports**. **455 are stable 1.0 candidates**
and three remain explicitly experimental:

- `conditional_transfer_entropy`;
- `discrete_transfer_entropy`;
- `return_map_stability`.

The compatibility route `fit_sparse_fpca_fdapy` remains a stable public name;
its backend-specific role is intentional and does not make it an accidental
alias of native `fit_sparse_fpca`.

The contract is stronger than a namespace count. It freezes the exact stable
name allow-list and cryptographic digests over the complete public namespace,
callable signatures, and result-container schema fields. Any disappearance,
silent replacement, signature change, result-field change, or unreviewed
widening therefore requires an explicit contract update and review.

This is a **candidate stability freeze**, not publication of 1.0. The public
1.0 compatibility promise is activated only by a later qualified final 1.0
release. No deprecation or removal is introduced by the freeze.

The programme path is now:

$$
0.12.0\ \text{scientific release closed}
\rightarrow
\text{product/API observation closed}
\rightarrow
\text{reproducibility evidence closed}
\rightarrow
\text{1.0 API boundary frozen}
\rightarrow
\text{literal 1.0 release-candidate qualification}.
$$

The observational predecessor is `PUBLIC_API_1_0_AUDIT.json`; the exhaustive
installed inventory is generated by `scripts/audit_public_api_surface.py`, and
`scripts/freeze_one_dot_zero_api.py` regenerates and verifies the frozen 1.0
boundary.

## Public API levels

### Canonical

Recommended default entry points for common scientific questions. The five
canonical routes are declared in `CANONICAL_WORKFLOWS.json` and documented in
the [canonical workflow guide](../workflows/index.md).

### Advanced

Supported and tested APIs for a more specific scientific need after the
canonical route is understood. Examples include sparse PACE FPCA, phase
analysis, full-refit mixed-effects bootstrap and exposure-aware generalized
prediction.

### Diagnostic

Inspection, sensitivity and audit APIs. They expose consequences of declared
choices but must not silently select the preferred model/specification.
Diagnostic status does not weaken name/signature stability once an API is in
the frozen stable boundary.

### Experimental

Supported code with a narrower validation or interpretation boundary. The
three experimental functions named above remain public and tested, but are
outside the 1.0 compatibility guarantee. Changing that status requires an
explicit update to the frozen stability contract.

## Naming conventions for new APIs

New public APIs should follow these conventions unless a scientific object
requires a clearer domain name:

- estimators: `fit_*`;
- resampling procedures: `bootstrap_*` when the operation is genuinely a
  bootstrap;
- plotting helpers: `plot_*`;
- tidy/tabular extractors: `*_frame`;
- manuscript wording: `*_reporting_text`;
- stochastic control: `random_state`;
- interval level: `confidence_level`;
- hierarchy identifiers: `participant_column` and `trial_column` where
  those concepts apply;
- result containers: descriptive CamelCase names ending in `Result` when the
  object represents the result of an analysis rather than a data container.

These are forward conventions, not grounds for mass-renaming established APIs.
After the 1.0 boundary freeze, a proposed new public API must also make an
explicit stability-status decision rather than entering the stable set
implicitly.

## 1.0 candidate decision rule

The completed D–G evidence showed that the non-experimental public surface has
coherent roles, workable end-to-end ergonomics, reproducibility/serialization
evidence, and no demonstrated scientific omission that requires an immediate
post-1.0 breaking change. That evidence is what authorizes the present freeze.

Test coverage alone is not sufficient. Age alone is not sufficient. Visual
symmetry across result objects is not sufficient. The frozen contract is not a
scientific claim that every API is equally important; it is a compatibility
boundary.

## Plotting stability rule

Every public `plot_*` API must remain represented by one deterministic
documented gallery case. This is a documentation contract, not a requirement
to manufacture a plot for every result object.

## Deprecation window

A stable 1.x public API scheduled for eventual removal should remain available
for at least **two subsequent minor releases** after the replacement is
introduced, unless retaining it would cause incorrect scientific results or a
security defect. Scientific-correctness exceptions must be documented
explicitly.

A future rename must:

1. introduce the canonical name before removing the historical name;
2. keep an explicit compatibility alias during the deprecation window where
   technically possible;
3. emit a targeted `DeprecationWarning` that names the replacement;
4. update examples, mathematical contracts and reporting documentation in the
   same change; and
5. document the earliest eligible removal release.

Deprecation is not an excuse to reinterpret an existing result object silently.
Changes to estimands, units, resampling units, clustering, denominator/exposure
semantics or uncertainty definitions require a new explicit contract.

No deprecation or removal is authorized by the 1.0 stabilization freeze.

## Historical stabilization decisions

Earlier stabilization work established the current hierarchy without removing
public statistical APIs. Historical names that do not perfectly match the
forward conventions remain available; established descriptive operations such
as `recurrence_matrix()`, `rqa_metrics()`, `dynamic_time_warping_distance()` and
`register_to_landmarks()` are not mechanically renamed.

The native sparse-FPCA transition deliberately used replacement-by-addition:

- `fit_sparse_fpca_fdapy()` remains the explicit compatibility backend;
- `fit_sparse_fpca()` is the separate native estimator;
- the native function is not a hidden call into FDApy; and
- coexistence alone is not grounds for deprecating the compatibility route.

The same distinction applies between common-grid `fit_mfpca()` and native
sparse paired-planar `fit_sparse_mfpca()`: they represent different observation
contracts, not duplicate spellings of one analysis.

## Argument consistency

The project audits but does not globally reorder historical signatures. New
APIs should keep required scientific objects positional only when their meaning
is unambiguous and place analysis choices behind keyword-only arguments where
possible.

Existing defaults remain unchanged unless a documented correctness issue
requires otherwise. Stable callable signatures are included in the frozen
contract digest, so an incompatible signature edit cannot pass the dedicated
1.0 API-stability gate silently.

## Failure semantics

Canonical workflows prefer explicit failure to silent repair. In particular,
the package should not silently:

- interpolate or convert missing values to zero;
- choose a model, family, correlation structure or sensitivity winner;
- infer grouped-binomial denominators or Poisson exposure;
- drop failed bootstrap refits;
- reinterpret participant/trial independence;
- clip scientifically meaningful uncertainty merely to satisfy physical bounds;
- or hide nonportable scientific state during serialization.

The full public surface remains in the [API reference](api.md); the exhaustive
capability list is separate from the recommended entry paths. The
[post-0.12 consistency audit](api-consistency-audit.md) records the evidence
that preceded the 1.0 boundary freeze.
